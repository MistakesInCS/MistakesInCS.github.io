## Introduction
I would describe what I did for the last month as clumsy stumbling. Or stupidity. Probably some combination of the two. I knew this wouldn't work, and yet I'm still somehow disappointed. 

I saw a paper a while ago that said something like neural nets can't unencrypt data. As expected, to some degree. I don't know a thing about information theory, and I know even less about how it relates to cryptography, so please excuse my butchering of terminology. In my vague intuition, encrypted data is prepared in such a way that each bit of the ciphertext has very little information about any given bit in the cleartext.

So I thought, Ok, makes sense, obfuscated information hinders learning. What about compression? It's kinda like encryption in the sense that it transforms data chaotically from one form to another, except it's also like the opposite of encryption since the compressor explicitly wants you to be able to recover the data. I knew this was probably a fool's errand, but on the offchance I could get it to work it would be pretty cool, and it's a good excuse to finally actually learn pytorch. I used MLPs, deconvolutions, LSTMs, and transformers, but spoiler, none of them really worked. I am either not clever enough to make up for my lack of compute, or not rich enough to make up for my lack of cleverness. In any case, I'm bored and want to think about other things that would either be more interesting or more rewarding.

## Setup

To quote the [Fashion-MNIST readme,](https://github.com/zalandoresearch/fashion-mnist/blob/master/README.md) "if it doesn't work on MNIST, it won't work at all." Therefore, I decided to work on MNIST data, and the plan is pretty simple: take the original MNIST image vector, compress it using zlib, then train neural nets using the compressed data as the feature and image as the target. Getting pytorch to work with this was pretty simple and straightforward. To actually make the data, I used the following code:

{% highlight python %}
self.compressed_data = [(list(zlib.compress(str(torch.flatten(feature).tolist()).encode())), feature)
                        for feature in data]
{% endhighlight %}

First, I take the MNIST image data (feature) and flatten it to form a 1D tensor. Then, I convert that to a python list. Then, I encode it, which turns the string into its byte-level form. Then, I compress that with zlib, creating a compressed form of the original data. Casting that to a list then gives a list of integers, where the i-th integer represents the i-th byte in the sequence. Here's some interesting trivia: the largest compressed MNIST image is 1359 bytes, and the smallest is just 67. For uncompressed MNIST, the largest is 9044, and the smallest is 3920. That's a massive size improvement! 

I think this is pretty well tokenized. I used 0 as a padding token originally, then -1e9 once I realized it probably wasn't good to pad with a number that has meaning in other contexts, but there are probably more sophisticated ways to do that for simple nnets. I use proper padding later when I pull out a transformer.

I first fed the data through several layers of MLPs, then followed up with a series of transposed convolutions (deconvolutions) to turn the 1D tensor into 2D image data. For this first run, I had the MLPs output a 512-long tensor, which then is directly fed into an initial 1x1 deconvolution with 1 channel per element in the tensor.

class NeuralNetwork(nn.Module):
  def __init__(self, max_size):
    super().__init__()
    self.flatten = nn.Flatten()
    self.linear_relu_stack = nn.Sequential(
        nn.Linear(max_size, 2048),
        nn.LazyBatchNorm1d(),
        nn.LeakyReLU(),
        nn.Linear(2048, 2048),
        nn.LazyBatchNorm1d(),
        nn.LeakyReLU(),
        nn.Linear(2048, 2048),
        nn.LazyBatchNorm1d(),
        nn.LeakyReLU(),
        nn.Dropout(0.1),
        nn.Linear(2048, 512),
        nn.LazyBatchNorm1d(),
        #nn.LeakyReLU(),

  def forward(self, x):

    logits = self.linear_relu_stack(x)
    return logits

# Code lovingly lifted from https://d2l.ai/chapter_generative-adversarial-networks/dcgan.html
# Bias to false because it's followed by a batch norm and the subtraction cancels the bias - thanks google
class LatentTo2dBlock(nn.Module):
  def __init__(self, in_channels, out_channels, kernel_size=2, stride=2, padding=0, bias=False):
    super().__init__()
    self.TransposedConv2d = nn.ConvTranspose2d(in_channels, out_channels,
                                kernel_size, stride, padding, bias=bias)
    self.batch_norm = nn.BatchNorm2d(out_channels)
    self.activation = nn.LeakyReLU()
  def forward(self, x):
    return self.activation(self.batch_norm(self.TransposedConv2d(x)))

class LatentTo2d(nn.Module):
  def __init__(self):
    super().__init__()
    self.Deconvolve = nn.Sequential(
        # Sizes from https://docs.pytorch.org/docs/stable/generated/torch.nn.ConvTranspose2d.html
        LatentTo2dBlock(in_channels=512, out_channels=128), # in: (512, 1, 1), out: (128, 2, 2)
        LatentTo2dBlock(in_channels=128, out_channels=32), # out: (32, 4, 4)
        LatentTo2dBlock(in_channels=32, out_channels=8, kernel_size=3, padding=(1,1)), # out: (8, 7, 7)
        LatentTo2dBlock(in_channels=8, out_channels=2), # out: (2, 14, 14)
        nn.ConvTranspose2d(in_channels=2, out_channels=1,
                           kernel_size=2, stride=2, padding=0, bias=True), # out: (1, 28, 28)
        nn.Sigmoid()
    )

  def forward(self, x):
    # Unsqueeze to go from size (512) to (512, 1, 1)
    return self.Deconvolve(x.unsqueeze(-1).unsqueeze(-1))

simple_nnet = nn.Sequential(NeuralNetwork(max_len), LatentTo2d())

# Alternatives

So I decided to try different architectures. I tried an LSTM, but I was stupidly defining it inside the scope of the forward function, which meant it wasn't saving the weights at all. That wasted a lot of time. The only redeeming part was that one time, the network "learned" to just make a little Bloodborne hunter guy for every number.

![Bloodborne](/assets/encoding/bloodborne.png)
_straight outta yharnam_

At this point I decided that the zip algorithm was probably too complex to learn, so I dumbed down the problem and took just one part of the algorithm: Huffman encoding. I whipped up a relatively simple algorithm for it and trained some models. Unfortunately, when I made the dataloaders, I left the batch size at 1, which made the models not learn anything and also take forever to train. I was really surprised that they didn't learn anything at all; I thought that batch size didn't really matter aside from getting different levels of approximation to the total loss function and going faster.

Anyway, the results from this weren't actually meaningfully different from the training done on the zipped files; just blurry, blobby 8s.

Once I realized that I made the LSTM wrong, I let it train for 50 epochs on the Huffman encoded data to... bad results.

At this point I started losing hope. I had the idea, inspired by word vector embeddings, to make embedding vectors for each example, even in the training set, and have the vectors "learn" to implement a distance function between their respective images. In specific, I wanted the dot product of any two embedding vectors to approximate the Euclidean distance between the original MNIST images. I then wanted to train to recreate the original images from the embedding vectors. Harebrained, I know. It's similar to multi-dimensional scaling, in a way.

But there's a problem: with the Euclidean distance, similar images have smaller distances, which means the learned embeddings would have a dot product close to 0, which means the embeddings for similar images would end up being mostly orthogonal to each other. So I switched to using a distance kernel instead; in particular, a radial basis function kernel. I tried some different minor tweaks as well but the results were largely uninteresting.

I was very stuck. I consulted the oracle at Gemini, and it suggested that since the L2 norm of an MNIST image is simply a measure of how bright it is, anything that uses the L2 norm would just measure the brightness. So really my embeddings are just comparing how bright the difference between two images is without actually capturing any of the nuance between _why_ they're different.

And then I tried to use a transformer. And oh boy...

# The Transformer

The transformer was a pain in the ass to get working. There was a lot of handwavy vagueness in my understand of the transformer that I had to work through, but probably the worst part was just how poorly documented the pytorch transformer is (in my opinion). The official docs kinda just drop the transformer down and say "it's a very basic implementation of the one in the original paper" and then don't actually describe what you need to do to get it working. I think probably half of the time spent on this was just troubleshooting the transformer, trying to feed it dummy input and googling the error messages I got. Online tutorials were also no help at all, since most of them basically copied the pytorch docs or had trivial and meaningless data, like tensors of random numbers.  Additionally, I didn't find any that actually _trained_ the transformer on anything; everybody just fed in a random tensor as source and target through the forward function and said "done!"

The Huffman encodings are pretty hard to learn, so to just see if I can get a working, learning transformer _at all_ I started out on arithmetic with only addition and multiplication: just learning the order of operations essentially. That's not very exciting, but I was pulling my hair out trying to get it to learn __anything__ at all. Was it the fault of the posiitonal encoder? What about the embedding layer? The transformer itself? The masking? The optimizer? Oh god. I looked at everything, it felt like. It turns out the biggest problem was that the transformer was too big. I had left it at the defaults, but that was way too big for this problem. It learned pretty OK with 4 encoder layers and 1 decoder layer and 4 heads. Any more than that and it refused to make progress at all. 

One neat thing about arithmetic is that I can create examples on the fly - just randomly generate a sequence of digits and operations, concatenate them into a string, and then run eval() on it to get the result. Super easy. And if the training set = test set = entire distribution, then there's no risk of overfitting. And that's what I saw, the learning slowed down quite a bit as it went on, but there was no end to learning gain.

To get a little more into the specifics of how I modeled arithmetic to the transformer, the source sequence was a sequence of digits and operators (addition or multiplication). The target sequence was then a sequence of digits forming the result. The model then had to generate each digit of the result one at a time. The trained models were able to do this successfully about 1/3 or 1/4 of the time. It's honestly super cool that it can even do that at all! It also had a lot of off-by-one errors, which I imagine is from a slightly incorrect probability distribution for those tokens. Again, super interesting that a transformer produces off-by-one errors. 

I'm sure that, had I let it train for a long time, it would have eventually learned to do arithmetic pretty convincingly. I mean, transformers can learn to talk pretty convincingly if you just let them train for a long time.

Anyway, there were some problems with my Huffman encoding procedure that prevented me from using it with a transformer immediately; in particular, it was incompatible with an embedding layer. Firstly, the values in the MNIST dataset are all floats, which don't easily translate to indices in an embedding matrix. Secondly, I had been packing the symbols and their respective counts in the string at the start, before the encoded string, so that the model could learn to implement the Huffman tree from those and then decode the entire string. This poses two problems: the first is that, since most MNIST images are blank space, there are a ton of 0s, and since the data are floats with a low likelhood of being identical, there's basically only one of each other element. The counts of each element would then be 1 or 600~. I had planned to use an embedding matrix with indices between 0 and 255ish, since those are the values of the bytes that the encoded and decoded strings would have (+ special tokens), but the potentially very large counts and float values threw a wrench in those plans. Instead, I did basically the same as the arithmetic models, and generated a random sequence of integers <= 255 to then Huffman encode on the fly.

Spoiler alertL this sucks. The model still can't really learn to decode these sequences, regardless of the model sizes I tried. It ends up just spitting out the END or START sequences for the entire sequence. If I keep training it for a while, it learns to guess some digits for each run; as an example, one of the models ended up outputting 81ENDENDEND... for every input. 

I'm pretty sad about this. It might be too difficult to learn to implement the entire Huffman tree from just the weights, but that's kinda the whole point. I also have the transformer predicting entire bytes from the encoded sequence. Working on bits might be easier, since a byte represents information from very probably multiple symbols, and is also less informative as a "previous" token in the target sequence, since it includes only partial amounts of the previous code. When given a byte, I'm asking it to understand what portion of the current symbol's code has already been written from the previous byte, and also finish the codes for the rest of the byte, but no more. That probably obfuscates a lot of the information.

I still think a transformer could learn this. After all, a model that could learn English could learn this. Unfortunately, I am not smart enough to overcome the bitter lesson, and not wealthy enough to swallow it.

# An Aside

As a small aside, I tried to see why the models struggled so much to learn compression/encoding, and basically came up with an intuitive argument that the algorithms create functions that aren't smooth enough. I think a big component of neural nets, in particular MLPs but probably also extending to transformers and other models, is that small changes in the input cause proportional changes in the output. A function with that property would be ideal for modeling, and a function without that property would be essentially impossible to model. I tried to think of a good metric for this: Lipschitz continuity seemed like a good one, but maybe it should be more directly captured by like, the error incurred by the best linear approximation through some interval of the function, since MLPs are basically linear approximators. I have no clue how to apply that line of thinking to transformers. I also thought about the biggest range of values in some neighborhood, but that's pretty similar to Lipschitz. Lipschitz doesn't really capture the idea of easy-to-learnness well; a very steep line has a high Lipschitz constant, and a large range of values in the neighborhood of some point, but is still trivial to learn, since it's a line. So I guess the best metric would be just the error from linear interpolation.

In any case, Huffman encoding and compression algorithms are highly chaotic and have huge variance in their outputs with small changes in their inputs. This is why modeling them is so difficult. At least, modeling them directly. I still think that this is well within the capabilities of a transformer, but I want to think about other things.
